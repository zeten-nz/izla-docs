## What was built (backend, `src/content-import/`)

- **`import-contract.ts`** — `schemaVersion = izlan-topic-content/v1`; size/count limits (body 5 MiB, ≤200 skills / ≤250
  lessons / ≤5000 activities / ≤100 skillRefs-lesson / ≤50 skillRefs-activity / ≤50 prereqs-lesson); supported activity
  types derived from the canonical Activity registry (markdown + objective contracts only); `documentHash` = SHA-256 over a
  canonical key-sorted serialization (arrays keep order). The hash is **not** an authorization/idempotency token.
- **`import-parser.ts`** (+ `import-parser.spec.ts`) — strict shape validation: rejects unknown top-level *and* nested
  fields, wrong types, duplicate contentKeys, duplicate skill codes; forbids server-owned fields; derives activity
  `position` from array order; reuses `validateActivityPayloadForAuthoring` (no second payload parser). Hard failures
  (non-object root / wrong schemaVersion / count-limit) throw `ContentImportError`; field issues are collected.
- **`import-validator.ts`** — pure resolution: skill reuse (ACTIVE by code) / conflict / archived / not-found; contentKey
  collision (create-only); prerequisite subject/status resolution; incremental whole-graph cycle detection over
  existing + batch edges via the existing `wouldCreatePrerequisiteCycle`.
- **`import.repository.ts`** — read snapshot (`lessonsByContentKeys`, `subjectSkills`) with the resolved Subject via the
  Topic→…→Subject chain; accepts an optional transaction client.
- **`import.service.ts`** — `validate()` dry-run and `apply()`. **apply()** = ONE Prisma transaction: authorize
  (`content.author` + SubjectAssignment for the **server-resolved** Subject) → **`SELECT … FOR UPDATE` on the destination
  Subject row** (the SAME serialization authority as the 2.2A-3 prerequisite writer) → **re-run full validation against the
  current DB** (dry-run never trusted) → create skills/lessons/revisions(v1)/activities/mappings/edges → write **ONE
  `content.import.apply` StaffAudit** (metadata = subjectId/topicId/documentHash/counts only). Unique-race → `IMPORT_CONFLICT`
  (409). Uses domain/repo primitives only — never HTTP, never a publication service.
- **`http/import.controller.ts`** — `POST /api/staff/content/topics/:topicId/import/{validate,apply}`, both `@RequirePermissions(content.author)`,
  `@Param('topicId', ParseUUIDPipe)`, `@Body() body: unknown` (strict parser owns validation). Out-of-scope Topic →
  `CONTENT_NOT_FOUND` (404, IDOR-safe).
- **`src/common/errors.ts`** — `ContentImportError(importCode, httpStatus)`, mapped in `auth-exception.filter.ts`.
- **`src/main.ts`** — Fastify `bodyLimit` raised to 5 MiB (the route body boundary).
- **`examples/izlan-topic-content.v1.json`** — a fake demo document (2 skills, 2 lessons, markdown + objective activities,
  LessonSkill + ActivitySkill, one prerequisite) that validates cleanly.

## Invariants preserved

- **No new learner surface** — everything imports as DRAFT (`publishedRevisionId=null`); import never publishes, transitions
  to REVIEW, overwrites, updates, or deletes.
- **Authorization** is permission-code + SubjectAssignment on the server-resolved Subject; no ADMIN bypass, no role-name
  check, no client-supplied Subject; out-of-scope Topic is IDOR-safe 404.
- **Secrets/answer keys** never appear in audit metadata, error payloads, logs, the dry-run summary, or the CMS; the raw
  document is never persisted or logged.
- **DAG serialization** reuses the Subject-row `FOR UPDATE` authority; a create-only import produces new lessons that are
  graph sinks, and the whole existing + batch edge set is validated for cycles inside the locked transaction.
- **Schema untouched** — migrations **23**, CHECK **46**, drift empty on dev + test.
