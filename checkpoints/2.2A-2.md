## Revision create / version algorithm
Backend authority: version = `max(existing version for Lesson) + 1` (first = 1), computed + created inside one transaction;
concurrency = `@@unique([lessonId, version])` with a **bounded retry (≤6)** around the version race (no locks/schema). Parent
Lesson must be **DRAFT or PUBLISHED** (ARCHIVED → 409); `Lesson.status` is never mutated. New revision `status = DRAFT`,
`createdBy = updatedBy = principal`. Client cannot supply id/lessonId/version/status/createdBy/updatedBy/reviewedBy/
publishedBy/publishedAt/estimatedDurationMin (whitelist → 400).

## Revision mutability + concurrency
Only DRAFT is mutable; PATCH edits `title` (required-if-present) / `description` (nullable-clearable); `updatedBy` = actor.
**Token:** `expectedUpdatedAt`; **DB boundary:** `updateMany WHERE id + updatedAt + status=DRAFT`; **stale:** 409
`CONTENT_EDIT_CONFLICT`, no write, no audit. REVIEW/PUBLISHED/ARCHIVED → 409 `CONTENT_NOT_DRAFT`.

## Activity concurrency authority (the revision aggregate)
Every Activity mutation carries **`expectedRevisionUpdatedAt`**. In one transaction: resolve revision + Subject → enforce
SubjectAssignment → **conditionally claim the DRAFT revision** (`touch`: `updateMany WHERE id+updatedAt+status=DRAFT`,
`data.updatedBy = actor`, count 0 → 409) → mutate Activity → StaffAudit → **return the new revision `updatedAt`** as the next
token. `Activity.updatedAt` is NOT the token; there is no extra version column.

## Activity contracts
- **create:** client supplies `type`, `position` (≥0), `payload`, optional `estimatedDurationMin` (≥0, bounded); server owns
  `source=HUMAN`, `aiMetadata=null`; source/aiMetadata/lessonRevisionId rejected (whitelist). Revision must be DRAFT.
- **PATCH:** `payload` and/or `estimatedDurationMin` only. `type` immutable (delete+recreate); `position` only via reorder —
  both rejected by whitelist.
- **delete:** DRAFT revision only; revision-token guarded; delete+touch+audit one transaction; unexpected FK → safe
  `CONTENT_DELETE_BLOCKED` (409), no FK detail.
- **reorder:** `PUT …/activities/order { orderedActivityIds, expectedRevisionUpdatedAt }`.

## StaffAudit
Actions: `content.revision.create|update`, `content.activity.create|update|delete|reorder`. Same-transaction as the business
write; rejected mutations write none; **reorder writes exactly ONE** event (targetType LessonRevision). Metadata = safe only
(lessonId, revisionId, revisionVersion, activityType, position, changed field names, schemaVersion) — **never** payload /
markdown / answerKey / correctOptionIds / raw body. Test CA2-32 asserts a sentinel secret answer never appears in any audit row.

## Reorder algorithm
Exact-set validation: unique ids, same count as the revision's current activities, no foreign id, no missing id (else
`CONTENT_REORDER_INVALID` 400). Collision-safe **two-step** inside one transaction: (1) set each to a unique negative
temporary `-(i+1)`; (2) set final `0..N-1`. Negatives never collide with each other or with existing `≥0` positions, so no
intermediate state violates `@@unique([lessonRevisionId, position])`. No partial commit; one audit event.
