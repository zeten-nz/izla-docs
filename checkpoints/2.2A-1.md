## Subject scope algorithm (§6/17)
Every child mutation resolves the Subject from DB relationships and requires the actor's SubjectAssignment; the
client-supplied subjectId is never trusted for entities that determine their own Subject:
- Track → `track.subjectId`
- Level → `level.track.subjectId`
- Module → `module.level.track.subjectId`
- Topic → `topic.module.level.track.subjectId`
- Lesson → `lesson.topic.module.level.track.subjectId`

`SubjectScopeService.requireScope(userId, subjectId|null)` throws `ContentNotFoundError` when the entity/parent is
missing OR the actor lacks the assignment — a single **IDOR-safe** 404; existence in another Subject is never revealed.
Subject create does not require a pre-existing assignment; it creates a self-assignment in the same transaction.

## Optimistic concurrency (§16)
- Request contract: every mutating PATCH/move carries `expectedUpdatedAt` (ISO-8601). Responses emit `updatedAt` as an
  ISO string so it round-trips exactly.
- DB conditional write: `updateMany({ where: { id, updatedAt: expected, status: DRAFT }, data })`. Precedence on the
  pre-loaded row: missing/out-of-scope → `CONTENT_NOT_FOUND` (404); not DRAFT → `CONTENT_NOT_DRAFT` (409); then a
  conditional write whose `count === 0` → `CONTENT_EDIT_CONFLICT` (409). No dedicated version column.
- Stale behavior: no write, no audit (both inside one transaction) — DB unchanged.

## Lesson.contentKey immutability (§11)
- Create: client supplies `contentKey` (non-empty, bounded charset; NOT generated, NOT inferred from title/slug).
- Update: `contentKey` is NOT in `UpdateLessonDto`; the global ValidationPipe (`whitelist` + `forbidNonWhitelisted`)
  **rejects** a PATCH body containing `contentKey` (also status/publishedRevisionId/createdBy/title) with 400 — not
  silently ignored. No DB trigger.

## Security invariants verified (§38)
- No ADMIN role-name bypass (permission-code only; zero role-name literals in runtime — only in a test assertion).
- `createdBy` always the principal (client value rejected). No client-controlled subject scope. No mass assignment
  (whitelist). No status / publishedRevisionId / contentKey mutation. No cross-subject reparent (only same-subject DRAFT
  Lesson→Topic move). No guessed-ID subject escape (IDOR-safe 404). Audit only inside the mutation transaction. No raw
  Prisma/SQL error leakage (P2002 → CONTENT_UNIQUE_CONFLICT). Staff routes gated by content.* permissions.
