## Skill authoring
- **Routes:** `GET|POST /subjects/:subjectId/skills`, `GET|PATCH /skills/:skillId`. No DELETE / archive / merge.
- **Create:** ACTIVE; client supplies name (+optional code/description/sortOrder); `subjectId`(route)/`status`/timestamps
  server-owned (rejected 400). No CEFR/skill enum hard-coded.
- **Patch:** name/code/description/sortOrder only; `subjectId`/`status` immutable (no cross-Subject move).
- **Lifecycle:** only ACTIVE skills editable; ARCHIVED → `CONTENT_SKILL_ARCHIVED` (409). No restore/archive via PATCH; no hard delete.
- **OCC:** `updatedAt` conditional (`status=ACTIVE`), strict-monotonic (`nextOptimisticTimestamp`); stale → 409; duplicate
  name/code → `CONTENT_UNIQUE_CONFLICT` (409, no P2002/SQL leak).

## LessonSkill
- **Routes:** `GET|POST /lessons/:lessonId/skills`, `DELETE /lessons/:lessonId/skills/:skillId`.
- **Subject invariant:** Skill Subject must equal the Lesson Subject; cross-subject → `CONTENT_NOT_FOUND` (IDOR-safe). Only ACTIVE skills assignable.
- **Lifecycle:** mutation only on a **DRAFT logical Lesson**; PUBLISHED/ARCHIVED → 409 `CONTENT_NOT_DRAFT` (read allowed).
- **OCC:** `Lesson.updatedAt` aggregate token (`expectedLessonUpdatedAt`); touch+mapping+audit in one transaction.
- **Idempotency:** existing add / missing remove with a CURRENT token → no-op (no advance, no audit); STALE token → 409 even for the already-final state.

## ActivitySkill
- **Routes:** `GET|POST /activities/:activityId/skills`, `DELETE /activities/:activityId/skills/:skillId`.
- **Subject invariant:** Skill Subject must equal the Activity's Lesson Subject; cross-subject → 404. Only ACTIVE skills.
- **Lifecycle:** mutation only when the owning **LessonRevision is DRAFT**; REVIEW/PUBLISHED/ARCHIVED → 409.
- **OCC:** `LessonRevision.updatedAt` aggregate token (`expectedRevisionUpdatedAt`), NOT `Activity.updatedAt`.
- **Idempotency:** same semantics as LessonSkill.

## Prerequisites
- **Routes:** `GET|POST /lessons/:lessonId/prerequisites`, `DELETE /lessons/:lessonId/prerequisites/:prerequisiteLessonId`.
- **Subject invariant:** both Lessons resolved from DB; Subjects must match; cross-subject → 404 (IDOR-safe). Actor assigned to the source Subject.
- **Source lifecycle:** DRAFT only (PUBLISHED/ARCHIVED read-only → 409).
- **Target lifecycle:** DRAFT or PUBLISHED; ARCHIVED → `CONTENT_PREREQUISITE_INVALID` (400).
- **Idempotency:** existing add / missing remove no-op with a CURRENT `Lesson.updatedAt` token; STALE → 409. Self-loop →
  `CONTENT_PREREQUISITE_INVALID` (400) at the service layer (DB CHECK `chk_lesson_prerequisite_no_self_loop` remains defense-in-depth).

## DAG prevention
- **graph orientation:** edge `{ lessonId → prerequisiteLessonId }` = "lessonId requires prerequisiteLessonId".
- **graph scope:** the WHOLE Subject graph (all edges whose source Lesson belongs to the Subject) — not just neighbours (§26).
- **algorithm:** `wouldCreatePrerequisiteCycle(edges, lessonId, prereqId)` = self-loop OR `hasPath(prereqId → … → lessonId)`;
  iterative (non-recursive) DFS (`prerequisite-graph.ts`, DAG-01..07 + 20k-deep-chain unit tests).
- **transaction serialization:** `PrerequisiteRepository.lockSubject` = `SELECT id FROM "subject" WHERE id = $1 FOR UPDATE`
  acquired inside the transaction BEFORE reading the graph + validating + writing; ADD and REMOVE both lock the same
  Subject row → all graph mutations for a Subject are serialized (no app-mutex/Redis/advisory-lock).
- **concurrent inverse-edge result:** DAG-E3 (Promise.all A→B and B→A) → exactly one 201, the other 409 cycle; the final DB
  graph is acyclic (both edges cannot coexist). Sequential DAG-E1/E2 also covered.
